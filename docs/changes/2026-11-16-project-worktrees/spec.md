# 按项目和 worktree 组织会话，并更换视觉风格

状态：开发中　阶段：dev-build　待关口：—　等级：L1　规模：标准　创建：2026-11-16　更新：2026-11-20

## 背景与目标

为什么要做：用户想在同一个项目（例如 `/Users/mac/github/devflow`）上同时开好几个会话、好几个 worktree 并行工作。daemon 已经能并行跑（实测），但桌面端只按机器把会话平铺成一列：worktree 会话的默认名是一串会话 id，看不出分支和所属项目；别处建好的 worktree（如 devflow 的 `.devflow-tmp/worktrees/<短名>`）在目录选择器里选不到；删会话时顺带删 worktree 和分支，会丢掉已提交未合并的工作，被保留下来的 worktree 又没有任何地方能再看到。另外，用户希望整体视觉风格改为参考图（T3 Code 截图）的样子，功能点不变。

做完的样子：侧边栏按 机器 → 项目 → worktree 组织，会话挂在所属 worktree 下；用户能在项目里新建带名字的 worktree、在任何已有 worktree 里开会话、用快捷键切换；会话和 worktree 分开收尾，删会话不再丢代码；整个 app 换成关口 A 选定的视觉方案，现有功能一个不少。

## 完成条件

R1–R9 的全部场景在 GUI 冒烟（CDP 驱动构建产物）里通过；`make check` 通过；`gui-smoke.mjs` 和 `gui-chat-smoke.mjs` 以本需求开始开发时 `change/dual-mode` 上的版本为基线，用例数量不减少、断言不放宽；协议在 `protocol.go` / `protocol.ts` / `docs/protocol.md` 三处一致。

## 现状（2026-11-16 调查，代码 + 临时 daemon 实测）

已经能用：
- 同一目录不勾 `-c` 可以开任意多个互不相干的会话，终端和对话可混用（实测）。
- 同一仓库可以同时开多个 Worktree 会话，终端和对话都行，无数量上限、无互斥（实测，`manager.go` 的 `beginCreate` 只串行化同 id 的并发创建）。
- 源目录可以选仓库子目录，会话落在 worktree 里对应的子目录（实测）。
- daemon 重启后 worktree 会话的身份不丢（终端靠 tmux 用户选项，对话靠 `chat-sessions.json`）。
- `/api/v1/sessions` 每条已带 `mode`，worktree 会话另带 `sourceWorkdir`、`sourceRepo`、`worktreeRoot`、`branch`；客户端只用了 `mode`。

卡住的地方（按严重程度）：
1. 删「工作区干净但有未合并提交」的 worktree 会话：返回 204，目录删除、分支被 `git branch -D`，提交只剩悬空对象；确认框不提 worktree 和分支（实测；`worktree.go:120-139` 只看 `git status --porcelain` 是否为空）。
2. 工作区不干净（含只有 gitignore 文件，如 `node_modules/`）时删会话：返回 409 `worktree_preserved`，会话已停并从列表消失，worktree 和分支留在磁盘，路径只在状态栏显示 6 秒，之后产品里没有任何地方能看到或清理它（实测）。
3. 单窗口，一次只显示一个会话，无分屏、无标签、无切换快捷键（`desktop/src/main/index.ts`、`renderer/index.ts:1079-1081`）。
4. 分不清谁是谁：worktree 会话默认名是会话 id（如 `1794824025040-12b763ac`）；同目录多个会话同名；侧边栏、工具栏、通知都不显示分支和源仓库；终端会话在侧边栏的顺序会随轮询随机互换（daemon 端 map 遍历）。
5. 勾了 `-c` 时，同一目录开第二个对话会话会被接到已有那个（`ready.existing`），开第二个终端会话报 fatal `claude_session_busy`；对话框的说明没讲这个后果。
6. Worktree 模式没有可填的字段：分支固定 `vibe/<会话id>`，目录固定 `<仓库父目录>/<仓库名>-worktrees/<会话id>`，基于源目录当前 HEAD、不含未提交改动；界面只有一句「创建一个隔离分支」。
7. 别处建的 worktree 打不开：目录选择器过滤所有 `.` 开头的目录、没有路径输入框，所以 `/Users/mac/github/devflow/.devflow-tmp/worktrees/general-skills` 选不到；即使选到，对话界面也因该路径未被 claude 信任而被拒（`workdir_untrusted`）。
8. 新 worktree 路径本身不在 claude 的信任记录里：之后无法在其中再开一个普通对话会话。
9. 没有任何 worktree 的列表、清理入口；daemon 没有对应 REST 端点。

视觉现状：样式集中在 `desktop/src/renderer/styles.css`（约 1060 行，23 个 CSS 变量，暖米色 + 赤陶色，CLAUDE.md 写明外壳对标 Claude Desktop）；终端配色写在 `index.ts` 的 xterm theme；没有深色模式。

## 前提

- P1 并行多开的后端能力已经有了；要解决的是界面怎么组织，以及 worktree 怎么建、怎么找、怎么收尾。（评审未提出异议，按推荐）
- P2 「项目」= 一个 git 仓库：它的所有 worktree（包括不是 vibe-remote 建的）归到同一个项目下，主目录是其中第一个 worktree；不在 git 仓库里的目录自成一个项目，下面只有它自己。（用户提出「机器、项目、项目的某个 worktree 或分支」三个维度，已确认方向）
- P3 会话和 worktree 的生命周期分开：结束或删除会话不再顺带删除 worktree 和分支；删除 worktree 是 worktree 上的显式操作，有未提交改动或未合并提交时明确告知。（按推荐）
- P4 每个 worktree 里的 claude 对话各自独立：新 worktree = 新对话，不继承主目录的上下文。（按推荐）
- P5 视觉风格参考用户给的 T3 Code 截图；只改外观和形态，不增加截图里的功能。（用户：「视觉风格修改下吧，功能点不变」）

## 做法与范围

做法：B 三层组织（机器 → 项目 → worktree，会话挂在 worktree 下），加上整体换视觉风格。放弃 A（只改显示）：解决不了已有 worktree 打不开、保留的 worktree 没人管；放弃 C（并排查看、git 操作）：工作量大，先推迟。

范围模式：缩减。

要做：
- 侧边栏三层组织，项目下列出该仓库全部 worktree（R1、R2）。
- 在项目里新建带名字的 worktree 并开会话（R3）；在任何已有 worktree 里开会话，含隐藏目录下的（R4）。
- 会话与 worktree 分开收尾：删会话保留 worktree；删 worktree 是单独操作，按改动和未合并提交分级确认（R5）。
- `-c` 的后果写进新建对话框（R6）。
- 切换会话的快捷键（R7，评审扩展 E1）。
- 换视觉风格：配色、圆角、间距，以及侧边栏条目、顶部标题、对话消息、输入框的形态（R8）。
- 新旧版本互连时降级而不是出错（R9）。

实施顺序上的约定：「有未合并提交时不删分支」这一处修复（现状 1）先单独做、单独提交，可先于其余部分合并（评审 Q4，未回复，按推荐）。

不做：
- 参考图里的功能：右侧信息面板（分支 / PR / 提交 / 改动统计 / 端口 / 用 VS Code 打开）、Working / Settled 分组与计数、搜索、模型选择器、附件与 @文件、语音输入、Steer、子任务卡片、滚动缩略条、布局切换按钮。理由：用户明确「功能点不变」；其中多项需要 daemon 新接口。
- 在工具里看 diff、合并、提 PR（E5）：交给会话里的 claude。
- 深色模式：现在没有，本次不加。
- 终端会话内容区的任何美化：终端模式纯字节透传，客户端不解析 PTY 输出。
- 把主目录的对话上下文带进新 worktree。
- 为没有 worktree 的分支单独列一行。

推迟到以后：
- E2 一个窗口里并排看 2 个会话（分屏）。
- E3 多个 macOS 窗口。
- E4 worktree 行上常驻显示「有未提交改动 / 领先 N 个提交」（删除确认时仍会现查现报）。
- 为已存在的分支创建 worktree（本次新建 worktree 总是新建分支）。
- 新建 worktree 时选择基于哪个分支（本次固定基于发起处当前 HEAD）。

已有可复用：
- `session/worktree.go`：创建、回滚、删除 worktree；`Manager.beginCreate`：同 id 并发创建串行化（新建幂等）。
- `/api/v1/sessions` 已下发的 `mode/sourceRepo/worktreeRoot/branch`。
- 对话可用性判定与置灰原因文案（`chat/availability.ts`、`info.chat`、`fs.chatTrust`）。
- 侧边栏状态点、桌面通知、重命名（名字存 tmux 用户选项 / `chat-sessions.json`）。
- `picker-layout.mjs`、`slash-menu-layout.mjs` 的布局测量方式（多档窗口尺寸下量可见性）。

理想状态对照：现状 会话按机器平铺，worktree 建了就没人管 → 本次 按项目和 worktree 组织，worktree 可命名、可找回、可安全收尾，外观换新 → 一年后 一个项目的多条并行工作线在一处总览（状态、改动、合并），可并排查看。

## 需求与验收场景

场景里的示例：机器 `this-mac`；项目 `devflow`（`/Users/mac/github/devflow`，主目录在 `main`）；它的另一个 worktree `/Users/mac/github/devflow/.devflow-tmp/worktrees/general-skills`（分支 `change/general-skills`，不是 vibe-remote 建的）。

### R1 侧边栏按 机器 → 项目 → worktree 组织

系统必须在每台机器下按项目分组显示会话，项目下按 worktree 分组，会话列在所属 worktree 下。

- **R1.1 一个项目两个 worktree 都有会话**
  假如 `devflow` 的主目录有 1 个对话会话，worktree `fix-login` 有 1 个终端会话
  当 用户看侧边栏
  那么 `this-mac` 下有项目 `devflow`；项目下有两行 worktree，分别显示 `main` 和 `fix-login`；两个会话各在自己的 worktree 下，带界面类型图标和状态点。
- **R1.2 项目只有一个 worktree**
  假如 `new-api` 只有主目录，有 2 个会话
  当 用户看侧边栏
  那么 不显示 worktree 这一层，2 个会话直接列在项目 `new-api` 下，项目行上显示当前分支名。
- **R1.3 不在 git 仓库里的目录**
  假如 会话的工作目录 `/Users/mac/notes` 不属于任何 git 仓库
  当 用户看侧边栏
  那么 它在名为 `notes` 的项目下，没有 worktree 层，也没有分支名和 worktree 相关的入口。
- **R1.4 同一 worktree 下多个未改名的会话**
  假如 `devflow` 的 `main` 下先后开了 3 个会话，都没改过名
  当 用户看侧边栏
  那么 3 个会话的显示名互不相同。
- **R1.5 顺序稳定**
  假如 一台机器有 3 个项目、共 8 个会话，期间没有新建或删除
  当 侧边栏连续刷新 40 次
  那么 项目、worktree、会话的先后顺序每次都相同：项目按名称，worktree 主目录在前、其余按分支名，会话按创建时间。
- **R1.6 折叠的项目里有会话在等用户**
  假如 项目 `devflow` 被折叠，其中一个对话会话出现待答的权限请求
  当 用户看侧边栏
  那么 `devflow` 这一行显示「等你处理」的状态点；展开后该会话行显示同样的点。
- **R1.7 标题和通知带上项目与分支**
  假如 当前打开的是 `devflow` / `fix-login` 下名为 `登录修复` 的会话
  当 用户看顶部标题，或该会话在后台触发桌面通知
  那么 标题和通知标题都包含项目名 `devflow`、分支 `fix-login` 和会话名。
- **R1.8 worktree 当前不在任何分支上**
  假如 某个 worktree 处于 detached HEAD
  当 用户看侧边栏
  那么 该行显示提交的短哈希，而不是空白。

### R2 列出项目的全部 worktree

系统必须在项目下列出该仓库的全部 worktree，包括没有会话的和不是 vibe-remote 创建的。

- **R2.1 别的工具建的、没有会话的 worktree**
  假如 `devflow` 有 worktree `general-skills`，没有任何会话
  当 用户看侧边栏
  那么 `devflow` 下有一行 `change/general-skills`，标明没有会话，行上有「新建会话」入口。
- **R2.2 项目的会话全部删除后**
  假如 `devflow` 的会话都被删除，仓库还有 2 个 worktree
  当 用户重启桌面端，或 daemon 重启
  那么 `devflow` 和它的 worktree 仍在侧边栏。
- **R2.3 从侧边栏移除项目**
  假如 项目 `devflow` 下没有会话
  当 用户选择「从侧边栏移除」
  那么 该项目不再显示；磁盘上的仓库、worktree、分支都不变；之后在该仓库任一目录新建会话，项目重新出现。
- **R2.4 项目下有会话时不能移除**
  假如 项目下还有会话
  当 用户打开项目的操作菜单
  那么 「从侧边栏移除」不可用，并说明要先结束会话。
- **R2.5 worktree 在别处被删掉**
  假如 用户在终端里执行了 `git worktree remove`
  当 侧边栏下一次刷新
  那么 那一行消失；如果它下面还有会话，会话仍显示在项目下并标明目录已不存在。
- **R2.6 worktree 不在允许的目录范围内**
  假如 仓库有一个 worktree 在 daemon 的 workdir 白名单之外
  当 用户看侧边栏
  那么 这个 worktree 不被列出。
- **R2.7 读不到 worktree 列表**
  假如 仓库目录被删除或 git 执行失败
  当 侧边栏刷新
  那么 项目行显示「读取失败」及原因，已有会话照常显示和可用。

### R3 在项目里新建带名字的 worktree

系统必须让用户从项目新建一个 worktree：填写名字，名字就是新分支名，基于发起处当前 HEAD。

- **R3.1 新建成功**
  假如 用户在 `devflow` 的 `main` 上发起「新建 worktree」，填 `fix-login`，界面选「对话」
  当 点确认
  那么 新分支 `fix-login` 基于 `main` 当前提交创建，worktree 目录是 `/Users/mac/github/devflow-worktrees/fix-login`；侧边栏 `devflow` 下出现 `fix-login`，并在其中打开一个新的对话会话。
- **R3.2 名字里有斜杠**
  假如 名字填 `change/foo`
  当 点确认
  那么 分支是 `change/foo`，目录名是 `change-foo`，侧边栏显示 `change/foo`。
- **R3.3 名字不合法**
  假如 名字为空、含空格、含 `..`、以 `-` 开头，或 git 不接受
  当 用户输入
  那么 对话框内显示原因，确认按钮不可用，不创建任何东西。
- **R3.4 分支名已存在**
  假如 仓库已有分支 `fix-login`
  当 点确认
  那么 对话框内提示分支已存在，不创建；对话框保持打开，可改名重试。
- **R3.5 目标目录已存在**
  假如 `/Users/mac/github/devflow-worktrees/fix-login` 已存在
  当 点确认
  那么 提示目录已存在，不创建、不覆盖。
- **R3.6 发起处有未提交改动**
  假如 `main` 的工作区有未提交改动
  当 对话框打开
  那么 对话框写明新 worktree 基于哪个分支的哪个提交，且不包含未提交的改动。
- **R3.7 创建中途断线**
  假如 确认后、会话就绪前连接断开
  当 客户端自动重连或用户点重试
  那么 只存在一个 `fix-login` worktree、一个分支、一个会话。
- **R3.8 创建失败**
  假如 git 创建 worktree 失败（例如磁盘满）
  当 点确认
  那么 显示 git 的错误信息；不留下半截目录或分支；侧边栏不出现新行。
- **R3.9 机器概览里的 Worktree 模式**
  假如 用户从机器概览新建会话，选「创建隔离 Worktree」
  当 对话框显示
  那么 出现同样的名字输入框和规则（R3.2–R3.6）；名字为空时确认按钮不可用。
- **R3.10 目标目录不在允许的范围内**
  假如 daemon 的 workdir 白名单只包含仓库本身，不包含 `<仓库父目录>/<仓库名>-worktrees/`
  当 用户在该项目里新建 worktree
  那么 提示该目录不在允许的范围内并写出路径，不创建目录和分支。

### R4 在已有 worktree 里开会话

系统必须让用户在项目下任何一个列出的 worktree 里新建会话。

- **R4.1 在 worktree 行上新建**
  假如 `devflow` 下有 `fix-login`
  当 用户点该行的「新建会话」
  那么 对话框标题带 worktree 名，并显示项目名和该 worktree 的完整路径；只让选界面（终端 / 对话）和启动选项，不出现目录列表和会话模式。
- **R4.2 隐藏目录下的 worktree**
  假如 worktree 在 `/Users/mac/github/devflow/.devflow-tmp/worktrees/general-skills`
  当 用户在该行新建终端会话
  那么 会话在该目录启动。
- **R4.3 主目录已被 claude 信任**
  假如 `devflow` 主目录在 claude 的信任记录里，`general-skills` 这个路径不在
  当 用户在 `general-skills` 上新建会话
  那么 「对话」可选，能正常创建对话会话。
- **R4.4 主目录和该 worktree 都未被信任**
  假如 项目主目录不在 claude 的信任记录里，`general-skills` 这个路径本身也不在
  当 用户在 `general-skills` 上新建会话
  那么 「对话」置灰，原因写明要先用终端界面在项目主目录打开一次 claude；「终端」可用。
- **R4.5 同一 worktree 再开一个**
  假如 `fix-login` 已有 1 个会话
  当 用户再新建一个，不勾 `-c`
  那么 得到第二个独立会话，两个可同时运行。
- **R4.6 worktree 本身已被信任**
  假如 项目主目录未被信任，但 `general-skills` 这个路径本身在 claude 的信任记录里
  当 用户在 `general-skills` 上新建会话
  那么 「对话」可选。

### R5 会话与 worktree 分开收尾

系统必须在删除会话时保留 worktree 和分支；删除 worktree 必须是 worktree 上的单独操作，并在会丢东西时先说明。

- **R5.1 删除 worktree 里的会话**
  假如 `fix-login` 下有 1 个会话，分支上有 2 个未合并的提交
  当 用户删除该会话
  那么 确认框写明 worktree 和分支会保留；确认后会话消失，`fix-login` 行仍在并标明没有会话，目录、分支、提交都在。
- **R5.2 删除干净且已合并的 worktree**
  假如 `fix-login` 没有会话、工作区干净、分支的提交都已被其他分支包含
  当 用户删除这个 worktree 并确认
  那么 目录和分支都被删除，该行消失。
- **R5.3 有未提交或未跟踪的文件**
  假如 `fix-login` 有 3 个未提交或未跟踪的文件
  当 用户删除这个 worktree
  那么 确认框写明有 3 个文件会被丢弃，默认按钮是取消；用户明确选「仍然删除」才删除；取消则什么都不变。
- **R5.4 只有被 git 忽略的文件**
  假如 `fix-login` 里只有 `node_modules/` 这类被忽略的文件，没有其他改动
  当 用户删除这个 worktree
  那么 按「干净」处理，不出现丢弃文件的警告；确认框另用一句话写明有 N 个被 git 忽略的文件会一并删除，N 为 0 时不显示这句话。
- **R5.5 有未合并的提交**
  假如 分支 `fix-login` 有 2 个提交不被任何其他本地分支或远程跟踪分支包含
  当 用户删除这个 worktree
  那么 确认框写明有 2 个未合并提交，提供「只删目录、保留分支」（默认）和「目录和分支都删」；选前者后目录消失、分支仍在。
- **R5.6 worktree 下还有会话**
  假如 `fix-login` 下有 2 个会话在运行
  当 用户删除这个 worktree
  那么 确认框写明会先结束这 2 个会话；确认后会话结束、worktree 按 R5.2–R5.5 处理。
- **R5.7 主目录不能删**
  假如 用户在项目的主目录这一行
  当 打开操作菜单
  那么 没有「删除 worktree」。
- **R5.8 不是 vibe-remote 创建的 worktree**
  假如 `general-skills` 是别的工具建的
  当 用户删除它
  那么 确认框标明它不是由 vibe-remote 创建；只删目录，分支一律保留；R5.3 的文件警告同样适用。
- **R5.9 开始删除之前就能发现的失败**
  假如 这个 worktree 现在删不了，而且在动手之前就能发现（例如它被 `git worktree lock` 锁定，或者里面还有别的 worktree 或子模块）
  当 用户确认删除
  那么 显示原因；会话、worktree 行和磁盘状态都不变。
- **R5.10 任何版本的桌面端删会话都不丢提交**
  假如 旧版桌面端连着新 daemon，worktree 会话的分支有未合并提交
  当 旧版桌面端删除该会话
  那么 删除成功；worktree 目录和分支都保留。
- **R5.11 worktree 不在任何分支上**
  假如 一个 detached HEAD 的 worktree 上有 2 个提交不被任何本地分支或远程跟踪分支包含
  当 用户删除这个 worktree
  那么 确认框写明这 2 个提交删除后不再属于任何分支，默认按钮是取消，用户明确选「仍然删除」才删除；没有这样的提交时按 R5.2–R5.4 处理。
- **R5.12 已经开始删除之后的失败**
  假如 会话已经被结束，或者 git 已经开始删除，之后才失败（例如某个目录没有权限删除）
  当 用户确认删除
  那么 如实显示 git 的错误信息和实际剩下的状态：会话已结束，目录可能只剩一部分，分支保留。

### R6 `-c` 的后果写在新建对话框里

系统必须在用户勾选「续上次会话」时，在对话框里说明同一目录已有会话正在用这段对话时会发生什么。

- **R6.1 目录里已有会话在用最近那段对话**
  假如 `devflow` 的 `main` 已有一个对话会话
  当 用户在同一 worktree 新建会话并勾选 `-c`
  那么 对话框显示一句说明：对话界面会切到已有的那个会话，终端界面可能无法启动；并提示不勾选即可开一段新对话。确认按钮仍可点。
- **R6.2 目录里没有会话**
  假如 该 worktree 下没有任何会话
  当 用户勾选 `-c`
  那么 不显示上面的说明。

### R7 用快捷键切换会话

系统必须提供切换会话的快捷键。

- **R7.1 按序号切换**
  假如 侧边栏当前可见的会话从上到下有 5 个
  当 用户按 ⌘3
  那么 第 3 个会话被打开。⌘1–⌘9 对应前 9 个；序号超出会话数时不动。
- **R7.2 上一个 / 下一个**
  假如 当前是第 5 个（最后一个）会话
  当 用户按 ⌘⇧]
  那么 回到第 1 个；⌘⇧[ 反向，同样循环。
- **R7.3 焦点在终端或输入框里**
  假如 焦点在终端里或对话输入框里
  当 用户按上述快捷键
  那么 照常切换，按键不被发送到远程或输入框。
- **R7.4 对话框打开时**
  假如 新建会话或确认对话框开着
  当 用户按上述快捷键
  那么 不切换。
- **R7.5 折叠的项目**
  假如 某项目被折叠
  当 用户按 ⌘⇧]
  那么 跳过其中的会话。

### R8 视觉风格

系统必须采用效果页的 M1 方案（贴近参考图：冷白加淡紫，主区域是浮起的圆角卡片，会话两行显示，用户消息是右对齐气泡）；外观以效果页 M1 为准，现有功能一个不少。

- **R8.1 对话会话**
  假如 用户打开一个有来回消息、工具调用和权限请求的对话会话
  当 看消息区
  那么 用户消息、助手消息、工具块、权限卡片、输入框的形态与选定方案一致；助手的 Markdown、代码块复制、diff、链接行为不变。
- **R8.2 终端会话**
  假如 用户打开一个终端会话
  当 看界面
  那么 外壳（侧边栏、标题、状态栏）和终端的底色、前景色、光标、选区颜色跟随新主题；终端内容仍是远程输出的原样显示。
- **R8.3 现有功能入口都在**
  假如 换成新风格
  当 跑现有的 `gui-smoke.mjs` 和 `gui-chat-smoke.mjs`
  那么 全部用例通过；用例数量不减少，断言不放宽（选择器可随结构调整）。
- **R8.4 可读性**
  假如 新配色
  当 量正文、次要文字、按钮文字与各自背景的对比度
  那么 正文和按钮文字 ≥ 4.5:1，次要文字 ≥ 3:1；「新消息 / 回合结束 / 等你处理」三种状态点在侧边栏底色上彼此可区分。
- **R8.5 小窗口和双语**
  假如 窗口是最小尺寸 800×500，界面语言分别为中文和英文
  当 打开侧边栏、新建会话对话框、删除确认框、斜杠菜单
  那么 没有文字重叠，主按钮都在窗口内且点得到。
- **R8.6 启动不闪**
  假如 冷启动应用
  当 窗口出现
  那么 窗口底色与新主题一致，没有旧配色或深色的闪烁。

### R9 新旧版本互连

系统必须在桌面端和 daemon 版本不一致时降级工作，而不是报错。

- **R9.1 新桌面端 + 旧 daemon**
  假如 daemon 是当前的协议 3
  当 新桌面端连上
  那么 侧边栏仍按项目和 worktree 分组显示已有会话（用会话自带的仓库和分支信息）；不显示没有会话的 worktree；在项目里新建命名 worktree、删除 worktree 的入口置灰并提示升级 vibe-remoted；机器概览里的 Worktree 模式保持旧行为（不出现名字输入框，自动命名）；删除 worktree 会话的确认框如实写明旧版 vibe-remoted 会在工作区干净时一并删除 worktree 和分支；其余功能照常。
- **R9.2 旧桌面端 + 新 daemon**
  假如 桌面端是当前版本
  当 连上新 daemon
  那么 新建、接入、删除会话都照常工作；旧版桌面端用 Worktree 模式新建时仍然成功，分支自动命名为 `vibe/<会话id>`；终端会话的帧与现在逐字节相同。

## 非功能要求

- 性能：一台机器有 20 个项目、每个 5 个 worktree 时，会话列表接口的响应时间比没有这些项目时多出不超过 200 ms。
- 安全：worktree 的创建和删除只作用于 daemon 自己从仓库读到的 worktree 和 workdir 白名单内的路径；客户端传来的名字只当作参数传给 git，不经过 shell；新增接口同样要求 Bearer token。
- 可靠性：创建失败要回滚（不留半截目录或分支）；删除在动手之前发现的失败保持原样并报错（R5.9）；已经结束会话或开始删除之后的失败如实报告实际剩下的状态（R5.12）。
