# 双模式会话（终端 + 对话）

状态：草案　阶段：dev-requirements　待关口：A　等级：L1　规模：标准　创建：2026-11-13　更新：2026-11-13

## 背景与目标

为什么要做：现在远程 claude 只能以 TUI 形式跑在 xterm 里。权限确认、计划审阅、选项提问都要靠键盘在终端里操作，长输出和 diff 也难读。想要 Claude Code VS Code 扩展那样的对话界面，只能回到本机 IDE，放弃「claude 跑在远程」这个前提。

做完的样子：同一个桌面 app 里新建会话时可以选「终端」或「对话」。终端会话的行为和现在一模一样。对话会话在远程 daemon 上用 stream-json 驱动 claude，首版功能对齐 VS Code 扩展（见「要做」）。客户端断线后，对话会话在远程照常跑；重连后按顺序补齐漏掉的消息，并重新显示没答的权限请求。

## 完成条件

R1–R19 的全部场景用 verify skill 跑通；gui-smoke 新增的对话模式端到端用例通过；`make check` 全绿；protocol-sync 检查三处一致；现有终端会话测试（`npm test`、`go test -race`、gui-smoke 原有用例）不改断言照样通过。

## 前提

- P1 终端模式的行为不变：PTY→tmux→任意 CLI，纯字节透传，tmux 保活、重连、幂等新建、fatal 错误码、存活检测都照旧。（已确认）
- P2 对话模式是第二条数据通路：daemon 用 stream-json + control protocol 驱动 claude，客户端只渲染结构化消息。CLAUDE.md 里「客户端绝不解析」这条约束的适用范围收窄到终端模式。改 CLAUDE.md 是人的决定（c1），在关口 A 确认。（已确认方向，c1 等确认）
- P3 客户端断开后，对话会话在远程继续跑；重连后按顺序补发漏掉的消息，并重新显示没答的权限请求。（已确认）
- P4 7 月的 headless 线（`feat/desktop-layout-redesign`，tip `69d8c70`）被放弃，是因为它的实现缺陷（断线即杀 claude、每个目录只有一个会话、只回放纯文本历史、服务端不缓存），不是方向错了。（假设，用户还没回答，见 H1）

## 做法与范围

做法：照搬 VS Code 扩展的做法——daemon 以 `-p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --permission-prompt-tool=stdio` 启动远程 claude，用 control protocol（initialize / interrupt / set_permission_mode / can_use_tool / control_cancel_request）交互，客户端把结构化消息渲染成对话界面。放弃的方案：解析 TUI 输出做富文本（违背纯字节透传约束，claude 每次改版都会坏）；在桌面本机跑 claude（违背「claude 跑在远程」这个前提）。
范围模式：选择性扩展

要做：
- 新建会话对话框加「界面」一节：终端 / 对话，默认终端。机器的 `claude_cmd` 不是 claude、claude 版本过旧或 daemon 协议过旧时，对话卡片置灰并写明原因（新建时检查）。原有的目录选择、普通/worktree、`claude_flags` 多选都保留。
- 对话模式下：勾选 `-c` 时显示该目录最近一次对话的完整历史；勾选 `--dangerously-skip-permissions` 时权限模式固定为 bypass。
- 流式消息和 Markdown 渲染。
- 工具调用块：Read / Grep / Bash 带输出，Edit / Write 显示行内 diff。
- 权限请求，提供扩展的 3 个选项：允许一次；允许并且不再询问（「对 <目录或范围> 里的 X 不再询问」，规则写进远程的 `.claude` 设置）；拒绝并附上说明。
- 计划审阅（3 个选项）、AskUserQuestion 表单。
- 中断（Esc / 停止按钮）、忙时排队发送。
- 斜杠命令列表（来自 `system/init.slash_commands`）。
- 权限模式切换：手动 / acceptEdits / plan；被固定为 bypass 时只显示 bypass。
- 断线保活和补发。
- 侧边栏圆点（灰：有新消息，绿：空闲，黄：等你处理），等你处理时发桌面通知。
- 出错状态：回合出错可重试；进程退出可重新启动，或「新建终端会话接上」；版本过旧时说明原因。
- 对话会话支持重命名 / 删除 / 重载（重载 = 用 `--resume` 同一 id 重启进程）。
- 「新建终端会话接上」：在同一目录新建终端会话，运行 `claude --resume <id>`，原对话会话标为已结束。
- 协议版本升到 3，`protocol.go` / `protocol.ts` / `docs/protocol.md` 三处一致。
- 更新 CLAUDE.md 的架构约束描述（c1）。

不做：
- 解析终端输出来做富文本界面（违背终端模式的纯字节透传约束）。
- 移动端、web 客户端（当前只维护桌面终端产品线）。
- 经手任何凭据：对话模式使用远程机上 claude 自己的登录，vibe-remote 不读、不存、不转发 claude.ai 凭据（Anthropic 政策不允许第三方产品代理 claude.ai 凭据；用户自己登录未修改的 claude 二进制是允许的）。
- `wss://`（传输安全模型不变）。
- 对话模式支持 claude 以外的 agent（stream-json 和 control protocol 是 claude 专有的；终端模式仍然 agent 无关）。

推迟到以后：
- @文件引用、图片附件。
- checkpoint / 回退 / 分叉。
- 模型选择器、上下文用量饼图。
- 已有会话就地切换界面。
- 多台桌面同时回答同一请求时，「先答先生效」以外的策略。

## 需求与验收场景

### R1 新建会话时选择界面

系统必须在新建会话对话框里提供「界面」选择（终端 / 对话，默认终端），并按选择创建对应类型的会话。

- **R1.1 默认新建终端会话**
  假如 用户打开新建会话对话框，没碰「界面」一节
  当 选好目录后点「新建」
  那么 创建的是终端会话，行为与本次改动前相同
- **R1.2 新建对话会话**
  假如 机器的 `claude_cmd` 是 claude，版本不低于最低版本，daemon 协议 ≥ 3
  当 用户选「对话」并新建
  那么 侧边栏出现带对话图标的新会话，右侧打开对话界面，输入框可用
- **R1.3 `claude_cmd` 不是 claude 时对话卡片置灰**
  假如 机器的 `claude_cmd` 是 `/bin/bash` 或 `codex`
  当 用户打开新建会话对话框
  那么 对话卡片不可选，并显示原因「对话界面只支持 claude」；终端卡片照常可用
- **R1.4 claude 版本过旧或 daemon 过旧时对话卡片置灰**
  假如 远程 claude 版本低于最低版本，或 daemon 报告的 `proto` < 3
  当 用户打开新建会话对话框
  那么 对话卡片不可选，并说明具体原因和需要升级的对象（claude 或 vibe-remoted）
- **R1.5 对话模式下勾选 `-c`**
  假如 该目录在远程有过对话记录，用户选「对话」并勾选 `-c`
  当 新建会话
  那么 对话界面显示该目录最近一次对话的完整历史（含工具块），之后发的消息接在这段对话后面
- **R1.6 对话模式下勾选 `--dangerously-skip-permissions`**
  假如 用户选「对话」并勾选 `--dangerously-skip-permissions`
  当 新建会话
  那么 权限模式显示为 bypass 且不可切换，工具调用不再弹权限请求
- **R1.7 worktree 和其他 flag 在对话模式下照常生效**
  假如 用户选「对话」+ worktree，并勾选了其他 `claude_flags`
  当 新建会话
  那么 claude 在新建的 worktree 目录里启动，勾选的 flag 都拼进了启动命令

### R2 同一会话 id 任何时刻只有一个 claude 进程

系统必须保证同一个会话 id 在远程任何时刻最多只有一个 claude 进程在跑。

- **R2.1 新建请求在 `ready` 前断线后重放**
  假如 用户新建对话会话，`ready` 到达前连接断开
  当 客户端自动重连或用户点 Retry，用同一个 `newSessionId` 重放
  那么 daemon 转为接入已在创建或已建好的会话，远程只有一个 claude 进程，侧边栏只有一个会话
- **R2.2 重载时旧进程先结束**
  假如 对话会话的 claude 进程还在跑
  当 用户点「重载」
  那么 旧进程确认退出后，才用 `--resume <同一 id>` 启动新进程；任一时刻 `ps` 里只有一个进程带这个 id
- **R2.3 交给终端时对话进程先结束**
  假如 对话会话的 claude 进程还在跑
  当 用户选「新建终端会话接上」
  那么 对话进程先结束，终端会话里的 `claude --resume <id>` 才启动
- **R2.4 两台桌面同时打开同一对话会话**
  假如 两台桌面都连着同一个对话会话
  当 两边分别发消息
  那么 两条消息按到达 daemon 的顺序进入同一个 claude 进程，两边都显示两条消息，没有启动第二个进程
- **R2.5 daemon 重启后**
  假如 daemon 重启前有一个对话会话在跑
  当 daemon 重启后用户打开这个会话
  那么 旧 claude 进程已经不在；会话显示为「已结束」，可以「重新启动」（`--resume`）或「新建终端会话接上」（见 Q2）
- **R2.6 两个对话会话勾 `-c` 指向同一份 claude 对话**
  假如 同一目录已有一个运行中的对话会话接着最近一次 claude 对话
  当 用户再新建一个对话会话并勾 `-c`
  那么 不启动第二个进程，而是打开已有的那个会话（或提示「这段对话已在 <会话名> 里打开」）

### R3 发送消息并流式显示回复

系统必须把用户输入发给对话会话的 claude，并在回复生成过程中逐段显示。

- **R3.1 正常发送**
  假如 对话会话空闲
  当 用户在输入框输入文字并按回车
  那么 用户消息立即出现在对话里，claude 的回复随生成逐段出现，结束后会话回到空闲
- **R3.2 Markdown 渲染**
  假如 回复里有标题、列表、表格、行内代码和代码块
  当 回复显示出来
  那么 按 Markdown 排版，代码块等宽显示并有复制按钮
- **R3.3 回复里有原始 HTML 或脚本**
  假如 回复里含 `<script>`、`<img onerror=…>` 或 `javascript:` 链接
  当 回复显示出来
  那么 这些内容以纯文本显示或被去掉，不执行任何脚本；普通链接用系统浏览器打开，不在 app 内跳转
- **R3.4 空输入**
  假如 输入框为空或只有空白
  当 用户按回车
  那么 不发送任何内容

### R4 显示工具调用

系统必须把 claude 的每次工具调用显示成一个工具块，包含工具名、参数摘要、状态和结果。

- **R4.1 Read / Grep**
  假如 claude 调用 Read 或 Grep
  当 工具执行完
  那么 工具块显示文件路径或搜索词，结果默认折叠、可展开
- **R4.2 Bash**
  假如 claude 调用 Bash
  当 命令执行完
  那么 工具块显示命令和输出，失败时标出错误状态
- **R4.3 Edit / Write**
  假如 claude 调用 Edit 或 Write
  当 工具块显示出来
  那么 显示文件路径和行内 diff（增删行分色）
- **R4.4 工具执行出错**
  假如 工具返回错误
  当 工具块更新
  那么 状态显示为失败，并显示错误内容

### R5 处理权限请求

系统必须把 claude 的权限请求（`can_use_tool`）显示成可操作的提示，并把用户的回答原样送回 claude。

- **R5.1 允许一次**
  假如 claude 请求运行一条 Bash 命令
  当 用户选「允许」
  那么 claude 执行该命令；下次同样的请求仍然会询问
- **R5.2 允许并且不再询问**
  假如 claude 请求运行 `npm test`，提示里给出「对 <目录> 里的 `npm test` 不再询问」
  当 用户选这一项
  那么 claude 执行命令，规则写进远程对应的 `.claude` 设置文件；之后同样的请求不再弹提示；本机不写任何规则文件
- **R5.2b 请求里没有「不再询问」的建议**
  假如 claude 的权限请求没有附带可保存的规则建议
  当 提示显示出来
  那么 只显示「允许」和「拒绝」两个选项
- **R5.3 拒绝并说明**
  假如 claude 请求编辑一个文件
  当 用户选「拒绝」并写「先别改这个文件」
  那么 claude 收到拒绝和这段说明，并接着回复；对话里记下这次拒绝
- **R5.4 断线期间来了权限请求**
  假如 客户端已断开，对话会话在远程继续跑
  当 claude 发出权限请求
  那么 claude 停在原地等待，不超时、不自动允许也不自动拒绝
- **R5.5 重连后重新显示没答的权限请求**
  假如 有一个权限请求在断线期间发出、还没回答
  当 客户端重连
  那么 补发完成后提示重新出现，回答后 claude 继续执行
- **R5.6 用户已回答，但回答在送达前断线**（最不能接受：回答没送到 claude）
  假如 用户点了「允许」，回答送达 daemon 前连接断开
  当 客户端重连
  那么 提示仍显示为没回答（不会显示「已允许」而 claude 实际还在等）；用户再次回答后 claude 继续执行
- **R5.7 重复回答**
  假如 同一个权限请求已经被回答（同一台桌面重复点，或另一台桌面先答了）
  当 又一个回答到达 daemon
  那么 daemon 忽略这个回答，claude 只收到第一个回答；后答的一端显示「已在别处处理」
- **R5.8 请求被 claude 取消**
  假如 提示显示期间 claude 发来 `control_cancel_request`
  当 客户端收到取消
  那么 提示关闭，标为「已取消」，不能再回答

### R6 审阅计划

系统必须在 claude 提交计划（ExitPlanMode）时显示计划全文和 3 个选项，并把选择送回 claude。

- **R6.1 批准并自动接受编辑**
  假如 claude 在 plan 模式下提交计划
  当 用户选「批准，自动接受编辑」
  那么 claude 开始执行，权限模式切到 acceptEdits，切换器同步显示
- **R6.2 批准并逐个确认**
  假如 同上
  当 用户选「批准，逐个确认」
  那么 claude 开始执行，权限模式切到手动，之后的编辑会弹权限请求
- **R6.3 继续完善计划**
  假如 同上
  当 用户选「继续完善」并写下意见
  那么 claude 留在 plan 模式，收到意见后修改计划
- **R6.4 断线期间提交的计划**
  假如 计划在断线期间提交
  当 客户端重连
  那么 计划审阅提示重新出现，行为同 R5.5

### R7 回答 AskUserQuestion

系统必须把 claude 的 AskUserQuestion 显示成表单，并把用户的选择送回 claude。

- **R7.1 单选和多选**
  假如 claude 提出一个单选题和一个多选题
  当 用户选好并提交
  那么 claude 收到每题的答案并继续
- **R7.2 自己填写**
  假如 题目允许其他答案
  当 用户选「其他」并输入文字
  那么 claude 收到这段文字作为答案
- **R7.3 没答完就提交**
  假如 还有题没选
  当 用户点提交
  那么 提交按钮不可用，标出没答的题

### R8 中断当前回合

系统必须让用户用 Esc 或停止按钮中断正在进行的回合。

- **R8.1 回复生成中中断**
  假如 claude 正在回复或执行工具
  当 用户按 Esc 或点停止
  那么 回合结束并标「已中断」，会话回到空闲，可以接着发消息
- **R8.2 有权限请求等待时中断**
  假如 一个权限请求在等待回答
  当 用户中断
  那么 提示关闭并标为「已中断」，claude 不执行该工具
- **R8.3 空闲时按 Esc**
  假如 会话空闲
  当 用户按 Esc
  那么 什么也不发生

### R9 忙时排队发送

系统必须允许用户在 claude 忙的时候继续输入，并在当前回合结束后按顺序发送。

- **R9.1 排队**
  假如 claude 正在回复
  当 用户再发两条消息
  那么 两条消息显示为「排队中」，当前回合结束后按顺序逐条发送
- **R9.2 撤回排队的消息**
  假如 有一条消息在排队
  当 用户删除它
  那么 它不会被发送
- **R9.3 中断时还有排队的消息**
  假如 有消息在排队
  当 用户中断当前回合
  那么 排队的消息退回输入框，不自动发送

### R10 斜杠命令列表

系统必须在输入 `/` 时列出当前会话可用的斜杠命令。

- **R10.1 显示可用命令**
  假如 会话已初始化
  当 用户在输入框开头输入 `/`
  那么 弹出 `system/init.slash_commands` 里的命令，可以继续输入过滤，选中后填入输入框
- **R10.2 终端专用命令**
  假如 用户手动输入 `/login` 或 `/theme`
  当 发送
  那么 显示「这条命令只能在终端界面使用」，并提供「新建终端会话接上」

### R11 切换权限模式

系统必须让用户在对话会话里切换权限模式，并显示当前模式。

- **R11.1 切换模式**
  假如 当前模式是手动
  当 用户切到 acceptEdits 或 plan
  那么 claude 收到 `set_permission_mode`，之后的行为按新模式执行，切换器显示新模式
- **R11.2 固定为 bypass**
  假如 会话以 `--dangerously-skip-permissions` 启动
  当 用户打开切换器
  那么 只显示 bypass，其他模式不可选，并说明原因

### R12 断线后保活与补发

系统必须在客户端断开时让对话会话在远程继续运行，并在重连后按顺序、无重复地补发漏掉的消息。

- **R12.1 断线期间继续运行**
  假如 claude 正在执行一个长任务
  当 客户端断开（关窗口、断网、休眠）
  那么 claude 进程不退出，任务继续执行；daemon 不发 exit 帧
- **R12.2 重连后补发**
  假如 断线期间 claude 产生了 50 条消息
  当 客户端重连
  那么 这 50 条消息按原顺序出现，没有重复，也没有缺漏；之后的新消息接着流式显示
- **R12.3 断线期间超过缓冲上限**
  假如 断线期间 claude 产生的消息超过每会话缓冲上限（见 H2）
  当 客户端重连
  那么 对话里显示「更早的 N 条消息已省略」，其后的消息完整、有序
- **R12.4 刚好在流式回复中途断线**
  假如 一条回复正在逐段生成
  当 客户端断线后重连
  那么 这条回复完整显示一次，没有半截重复

### R13 出错与进程退出

系统必须在回合出错或 claude 进程退出时显示明确的状态，并提供恢复办法。

- **R13.1 回合出错**
  假如 claude 返回错误结果（例如 API 出错）
  当 回合结束
  那么 对话里显示错误内容和「重试」，重试会重新发送上一条用户消息
- **R13.2 claude 进程真退出**
  假如 claude 进程退出或崩溃
  当 daemon 发现进程结束
  那么 daemon 发 exit 帧；对话界面显示「会话已结束」，提供「重新启动」（`--resume` 同一 id）和「新建终端会话接上」
- **R13.3 只有真退出才发 exit**
  假如 客户端主动断开或网络断开
  当 daemon 拆掉这条连接
  那么 不发 exit 帧，会话在侧边栏保持运行中
- **R13.4 启动后发现版本不支持**
  假如 claude 启动后 `system/init` 里没有 `claude_code_version`，或版本低于最低版本（H3）
  当 daemon 处理 init
  那么 会话以 fatal 错误结束，界面显示「claude 版本过旧」和需要的版本，并提供「新建终端会话接上」；客户端不自动重连

### R14 交给终端接着做

系统必须让用户把对话会话交给一个新的终端会话，在同一目录用 `claude --resume <id>` 接着做。

- **R14.1 交接**
  假如 对话会话出错，或用户想用终端专用命令
  当 用户点「新建终端会话接上」
  那么 在同一目录新建终端会话，运行 `claude --resume <id>`，能看到之前的对话；原对话会话标为「已结束」，输入框不可用
- **R14.2 对话会话还有回合在跑**
  假如 claude 正在回复
  当 用户点「新建终端会话接上」
  那么 先提示「当前回合会被中断」，确认后先中断并结束对话进程，再启动终端会话

### R15 重命名、删除、重载对话会话

系统必须让对话会话和终端会话一样支持重命名、删除和重载。

- **R15.1 重命名**
  假如 有一个对话会话
  当 用户双击侧边栏名字改名
  那么 新名字保存在远程，其他桌面和 daemon 重启后都显示新名字
- **R15.2 删除**
  假如 对话会话正在运行
  当 用户删除它
  那么 claude 进程结束，会话从侧边栏消失；远程 `~/.claude/projects` 下的对话记录保留
- **R15.3 重载**
  假如 对话会话卡住或出错
  当 用户点「重载」
  那么 用 `--resume` 同一 id 重启进程（满足 R2.2），历史保留，可以接着对话

### R16 侧边栏状态与桌面通知

系统必须在侧边栏标出每个对话会话的状态，并在会话等你处理时发桌面通知。

- **R16.1 有新消息**
  假如 对话会话不是当前打开的会话
  当 它收到新消息
  那么 侧边栏显示灰点；打开该会话后点消失
- **R16.2 回合结束**
  假如 对话会话不是当前打开的会话
  当 它的回合结束
  那么 侧边栏显示绿点
- **R16.3 等你处理**
  假如 窗口没有聚焦，或该会话不是当前打开的会话
  当 它收到权限请求、计划审阅或 AskUserQuestion
  那么 侧边栏显示黄点，并发桌面通知（未签名 app 降级为 Dock 弹跳加角标）；点通知打开该会话
- **R16.4 不需要配 hook**
  假如 远程没有配置任何 claude hook
  当 对话会话的状态变化
  那么 R16.1–R16.3 照常工作（状态直接来自结构化消息）

### R17 终端模式行为不变

系统必须让终端会话的行为与本次改动前完全一致。

- **R17.1 现有回归测试**
  假如 本次改动已合入
  当 跑 `make check` 和 gui-smoke 原有用例

- **R17.2 新桌面连旧 daemon**

  当 新桌面连上并新建终端会话
  那么 终端会话正常工作；对话卡片置灰并提示升级 vibe-remoted（R1.4）
- **R17.3 旧桌面连新 daemon**

  那么 终端会话正常工作；旧桌面的会话列表里出现的对话会话不会被当成终端会话打开（打开时给出明确错误）

### R18 协议升到 3 并保持三处一致

- **R18.2 三处一致**

### R19 更新 CLAUDE.md 的架构约束（c1）

系统必须在 CLAUDE.md 里说明两条数据通路，并把「客户端绝不解析」的约束限定在终端模式。

- **R19.1 文档更新**
  假如 关口 A 时用户确认了 c1
  当 本次改动合入
  那么 CLAUDE.md 写明：终端模式纯字节透传、不解析；对话模式由 daemon 驱动 claude 的 stream-json，客户端渲染结构化消息；对话模式只支持 claude

## 非功能要求

- 性能：局域网下，发送后第一个可见字的时间，不比同一台机器上直接用 CLI 慢 200ms 以上（实测记录，不做硬保证）；重连后补发 500 条消息，渲染完成 ≤ 2 秒。
- 安全：权限规则只写在远程机器上；客户端不保存、不经手任何 claude 凭据；模型输出经过 sanitizer 渲染 Markdown，不插入模型给出的原始 HTML。
- 兼容：新增帧和字段在接收端一律可选，沿用 protocol.md 的兼容规则。
